# Android App 高级感 UI 设计规范（Kotlin）

**版本：** v1.0  
**视觉方向：** Quiet Premium（克制、清晰、细节精致）  
**适用范围：** Kotlin Android App；Jetpack Compose 优先适配，也兼容传统 XML/View。  
**目标：** 在不牺牲可用性、可访问性和原有业务逻辑的前提下，统一视觉语言，降低“模板感”和廉价感。

---

## 1. 设计原则

### 1.1 核心气质

- **克制而非堆料：** 以留白、排版、层次和细节建立质感，而不是靠渐变、玻璃拟态、大面积阴影或装饰图案。
- **内容优先：** 用户最重要的信息先出现；操作入口明确；装饰永远不能压过内容。
- **一致而有节奏：** 全 App 只维护一套颜色、间距、圆角、字体和组件规则；页面可以有变化，但不能各自发明一套样式。
- **原生、轻量、可信：** 沿用 Android 交互习惯与系统能力，不为追求“像 iOS”而生硬移植导航、弹窗和手势。
- **状态完整：** 页面不只设计成功态，还必须有加载、空数据、错误、禁用、权限不足和操作反馈。

### 1.2 默认视觉方向

采用**浅灰底色 + 白色内容面 + 深色正文 + 单一低饱和品牌强调色**。默认强调色使用沉稳的靛蓝；如果项目已有成熟品牌色，应保留品牌识别并将其映射到语义色角色，不要为了套用本规范而硬换颜色。

### 1.3 明确禁止的常见问题

- 不要让每一块内容都变成圆角卡片；优先通过留白、对齐和细分隔线组织内容。
- 不要同时使用多套圆角、字体、阴影和强调色。
- 不要把渐变、彩色描边、发光、玻璃拟态当作“高级感”的默认手段。
- 不要滥用超大标题、全粗体、胶囊按钮和悬浮按钮。
- 不要用 emoji 代替正式功能图标；不要混用不同线宽、不同风格的图标。
- 不要为了截图好看而缩小正文、压缩点击区域或隐藏关键操作。
- 不要只修首页；所有主要页面、弹窗、设置项、空状态和错误状态必须使用同一套规则。

## 2. 颜色系统

颜色必须定义为**语义 Token**，组件通过主题角色取色，不允许在页面中散落大量硬编码颜色。

### 2.1 默认浅色主题

| Token | 建议色值 | 用途 |
|---|---|---|
| `background` | `#F6F7F9` | 页面背景，避免刺眼的纯白铺满全屏 |
| `surface` | `#FFFFFF` | 主内容区域、输入框、浮层 |
| `surfaceSecondary` | `#EEF0F4` | 次级容器、筛选区、图标底 |
| `textPrimary` | `#171A22` | 标题和主要正文 |
| `textSecondary` | `#646B78` | 描述、次要信息 |
| `textTertiary` | `#858C99` | 时间、辅助标签等弱信息 |
| `outline` | `#DDE1E8` | 输入框边界、分隔线；避免过重描边 |
| `primary` | `#4C5BD4` | 唯一主要操作色、选中状态、关键链接 |
| `onPrimary` | `#FFFFFF` | 主色按钮内文字/图标 |
| `primaryContainer` | `#E9ECFF` | 轻量选中底、次级强调底 |
| `success` | `#267A57` | 成功状态 |
| `warning` | `#946200` | 警告状态 |
| `error` | `#B3261E` | 错误、破坏性操作 |

### 2.2 默认深色主题

| Token | 建议色值 | 用途 |
|---|---|---|
| `background` | `#101116` | 页面底色 |
| `surface` | `#171920` | 主内容面 |
| `surfaceSecondary` | `#222630` | 次级容器 |
| `textPrimary` | `#F1F2F6` | 主要文字 |
| `textSecondary` | `#B4BAC6` | 次要文字 |
| `textTertiary` | `#8991A1` | 弱化信息 |
| `outline` | `#383E4A` | 边界与分隔线 |
| `primary` | `#B8C0FF` | 深色主题中的强调色 |
| `onPrimary` | `#22295D` | 主色内容文字 |
| `primaryContainer` | `#2B3158` | 轻量强调容器 |
| `success` | `#83D6AE` | 成功状态 |
| `warning` | `#F2C879` | 警告状态 |
| `error` | `#FFB4AB` | 错误状态 |

以上是默认基线，正式落地时需检查文本/背景的实际对比度。状态不能只用颜色表达，还应配合图标、文案或形状。深色主题不应把浅色主题简单反色，也不要使用纯黑背景搭配高亮霓虹色。

### 2.3 颜色使用规则

1. 每屏只允许一个主要视觉焦点；主色优先留给主要操作和明确的选中态。
2. 普通页面以中性色为主，彩色面积建议控制在少数重点区域。
3. 禁止无意义的彩色渐变和每张卡片使用不同颜色。
4. 危险操作使用错误色，但正常状态、普通信息不能一律套用红/绿/蓝。
5. 可考虑 Android 动态取色，但只有当它不会破坏品牌识别、图表含义和状态一致性时才启用。

## 3. 排版系统

优先采用 Android 系统默认字体栈。中文界面跟随系统中文字体回退，不应为了所谓“高级”强行引入体积较大的字体文件。标题、正文和辅助文案应形成明确层级，避免一屏所有文字都一样大或一样粗。

| Token | 字号 / 行高 | 字重 | 使用场景 |
|---|---:|---|---|
| `display` | 32 / 40 sp | SemiBold | 少量首页核心数据或欢迎页主标题 |
| `pageTitle` | 26 / 34 sp | SemiBold | 页面主标题 |
| `sectionTitle` | 20 / 28 sp | SemiBold | 内容分区标题 |
| `cardTitle` | 16 / 24 sp | Medium | 卡片/列表主标题 |
| `bodyLarge` | 16 / 24 sp | Normal | 重要正文、核心说明 |
| `body` | 14 / 22 sp | Normal | 常规正文、列表副标题 |
| `label` | 13 / 18 sp | Medium | 表单标签、按钮和状态标签 |
| `caption` | 12 / 16 sp | Normal | 时间、辅助说明、次要元数据 |

### 排版约束

- 页面主标题通常左对齐，除非欢迎页、完成页等明确需要居中构图。
- 正文优先使用 14–16sp；12sp 只用于非关键辅助信息，不可用于关键说明或主要操作。
- 中文多行文本应留出舒适行高；避免紧凑到像日志、控制台或表格。
- 同层级的字体大小、粗细和颜色必须统一；不要用粗体来替代正确的信息结构。
- 数字、金额、时间等高频比较字段尽量保持稳定对齐；适合时使用等宽数字。
- 适配系统字体缩放，不能通过固定高度裁掉放大后的文字。

## 4. 间距、布局和尺寸

采用 4dp 基础、8dp 主节奏的间距系统。优先使用以下 Token，不要随手写出大量不规则数值。

| Token | 数值 | 典型用途 |
|---|---:|---|
| `space4` | 4dp | 图标与文字的微间距 |
| `space8` | 8dp | 紧密相关元素之间 |
| `space12` | 12dp | 列表主副信息、控件内分组 |
| `space16` | 16dp | 卡片内边距、常规组件间距 |
| `space20` | 20dp | 手机页面左右边距、卡片舒适内边距 |
| `space24` | 24dp | 区块之间 |
| `space32` | 32dp | 主要内容组之间 |
| `space40` | 40dp | 页面级大分隔 |
| `space48` | 48dp | 少量大面积留白 |

### 布局规则

- 手机页面左右边距通常为 20dp；密集型工具页可使用 16dp，但同一页面需保持一致。
- 相关元素靠近，不相关区块拉开距离；不要用线条分隔每一行。
- 列表、设置页优先使用整齐的行高和分组标题；复杂信息可用卡片，但避免多层卡片嵌套。
- 内容宽度增加时应限制正文最大宽度或采用双栏/主从布局，不要把手机纵向布局简单拉宽。
- 页面容器应响应状态栏、导航栏、软键盘和系统手势区域，不能通过写死顶部 padding 来“碰运气”。
- 所有尺寸使用 `dp`，字体使用 `sp`；不得使用物理像素 `px` 作为布局常量。

## 5. 圆角、边框和层次

统一圆角层级，整套应用尽量只使用以下几档：

| Token | 建议值 | 用途 |
|---|---:|---|
| `shapeSmall` | 8dp | 小标签、紧凑控件 |
| `shapeMedium` | 12dp | 输入框、次级按钮 |
| `shapeLarge` | 16dp | 标准卡片、主要按钮 |
| `shapeExtraLarge` | 24dp | 大型弹窗、重点内容面 |
| `shapeFull` | 全圆角 | Chip、圆形图标按钮等特定组件 |

- 不要让所有元素都使用 24dp 或全圆角；圆角应体现组件层级。
- 普通内容面优先靠底色差形成层次，阴影仅用于确实浮起的菜单、对话框、拖拽对象等。
- 边框使用低对比中性色；避免给每个组件同时加粗边框、阴影和高亮底色。
- 选中态优先使用底色、字重、图标或细节变化表达，不要所有选中项都加粗描边。

## 6. 核心组件规范

### 页面顶部栏

- 标准顶部栏以 56dp 为基准，返回、标题和操作按钮垂直居中。
- 标题长度较长时要有截断或折行策略，避免与右侧操作冲突。
- 只有信息层级确实需要时才采用大标题；不要每个二级页面都做大标题占据首屏。

### 主按钮与次按钮

- 主按钮高度建议 48–52dp，使用主色实底和高对比文字。
- 同一屏只设置一个视觉上最突出的主要操作；次要操作使用描边、浅底或文字按钮。
- 按钮文案用动词开头且能说明结果，例如“保存设置”“重新连接”，避免“确定”“操作”等模糊文本。
- 加载中的按钮应有明确状态并避免重复提交；禁用态要可辨识但仍可读。

### 输入框与表单

- 标准输入控件高度建议 52–56dp；标签、输入内容、提示和错误信息各有明确层级。
- 焦点态使用主色细边框或浅色底，避免粗亮边框和大面积发光。
- 校验信息放在字段附近；不要只用 Toast 告诉用户哪个输入有问题。
- 错误状态必须说明如何修正；敏感操作需要清晰的确认和取消路径。

### 卡片与列表

- 卡片内边距 16–20dp；卡片之间 12–16dp。卡片只用于有独立语义的一组内容。
- 普通设置列表更适合使用整洁行布局、轻分隔线和分组标题，而不是每一项都包成卡片。
- 点击行的可交互范围应覆盖合理的整行区域，并提供明确的反馈。
- 主信息一行优先；副信息最多两行，超出时按内容性质采取展开、截断或详情页，而不是让整页高度失控。

### 导航

- 顶级目的地为 3–5 个时可使用底部导航，并保持图标、标签、选中态完整。
- 更深层页面使用顶部返回导航；不要把所有功能都塞进底部栏。
- 当前所在位置必须清楚；导航切换后应保持符合预期的状态和滚动位置。
- 大屏/横屏不应机械沿用手机底栏，应根据可用宽度考虑 NavigationRail、导航抽屉或主从布局。

### 图标与插图

- 优先使用项目当前已采用的 Material Symbols / Material Icons / 同一套矢量图标库。
- 默认图标视觉尺寸 20–24dp，线宽、填充风格和光学尺寸保持一致。
- 图标按钮需要有语义描述；仅装饰的图形不应干扰屏幕阅读器。
- 插图只用于空状态、引导或有实际意义的内容，不要为了填满空间加入无关装饰。

## 7. 动效与交互反馈

- 动效的目的是帮助用户理解状态变化，而不是展示技术效果。
- 常规过渡建议 160–240ms；小型反馈可以更短；大型页面转场应更克制。
- 优先使用淡入淡出、轻微位移、容器变形和 Material 组件已有反馈；避免弹跳过强、无意义循环动画。
- 点击后要有即时可见反馈；网络操作要有加载、成功或失败结果。
- 动效不得阻塞关键操作；尊重系统动画缩减设置，并避免低性能设备上持续消耗资源。

## 8. 必须完整设计的状态

每个需要数据、网络、权限或用户输入的页面，都应明确处理：

1. **Loading：** 使用轻量进度指示或结构化骨架屏；不能整页无反馈，也不要所有页面都用闪烁骨架。
2. **Empty：** 解释为什么为空，并给出合理的下一步操作；不要只留一片空白。
3. **Error：** 使用普通语言说明发生了什么、用户能做什么；提供重试或恢复路径。
4. **Success：** 给出明确、短暂且不打断工作的反馈；避免每次操作都弹出大对话框。
5. **Disabled / Permission denied：** 区分暂不可用与无权限，并尽可能说明原因。
6. **Destructive action：** 删除、清除、重置等操作应明确后果；必要时提供确认、撤销或恢复机制。
7. **Long content：** 处理长标题、超长用户名、空字段、极端数字、多行错误和小屏幕布局。

## 9. 深色模式、无障碍与适配

### 深色模式

- 维护独立的 Light/Dark 语义色映射，禁止通过简单反色生成深色主题。
- 深色界面依靠不同深灰层级表达结构，避免全黑背景上堆叠多个亮色卡片。
- 图片、图表、状态色和品牌标志需要单独检查深色可读性。

### 无障碍

- 可点击目标建议至少达到 **48 × 48dp**；若可见图标较小，可扩大触摸区域。
- 颜色不是唯一信息载体；状态还需通过文字、图标或形状表达。
- 为非文本控件提供有意义的语义描述；检查 TalkBack 焦点顺序和控件角色。
- 支持系统字体缩放，不裁切文本、不让按钮文字溢出；测试高对比度和色觉差异场景。

### 屏幕适配

- 至少检查紧凑手机宽度、横屏、分屏窗口和较大屏幕。
- 当可用宽度达到约 600dp 或更大时，评估是否切换导航模式、使用双栏或主从布局；具体断点应基于应用的内容结构，而非只按设备型号判断。
- 不应将应用锁定为只能竖屏；布局应能响应折叠、展开、窗口调整和键盘出现。

## 10. Kotlin 项目实施要求

### 10.1 先识别现有 UI 技术栈

- 如果项目已使用 **Jetpack Compose**：基于 `MaterialTheme` 统一 `ColorScheme`、`Typography`、`Shapes`，将 Token 集中放在主题/设计系统模块中。
- 如果项目使用 **XML + Views**：沿用现有架构，以 `colors.xml`、`dimens.xml`、`themes.xml`、样式和共享组件实现相同规范。
- 不要仅仅为了换 UI 就把 XML 全量重写成 Compose，也不要为了“现代化”随意更换导航、状态管理或网络架构。

### 10.2 代码组织建议

Compose 项目可按现有目录结构合理组织为：

- `ui/theme/Color.kt`：语义颜色与浅/深主题映射。
- `ui/theme/Type.kt`：统一文字样式。
- `ui/theme/Shape.kt`：统一圆角层级。
- `ui/theme/Theme.kt`：主题入口、系统主题与可选动态颜色策略。
- `ui/components/`：应用级共享组件，如页面标题、设置行、状态视图、主按钮等。
- `ui/screens/`：页面结构只消费设计 Token 和共享组件，不直接定义一套临时样式。

具体目录名称以仓库现状为准，不要求机械照搬。

### 10.3 实施限制

- 优先做**设计系统统一和页面重构**，保留原有业务逻辑、数据流、导航目的地、权限行为和状态管理。
- 不随意升级 Gradle、Kotlin、Compose BOM 或其他依赖；只有在必要且兼容性明确时才修改。
- 不引入庞大的 UI 库或网络字体，只为常规圆角、阴影和简单动效增加依赖。
- 不允许仅做静态截图式页面：所有原有按钮、表单、开关、列表与导航必须继续正常工作。
- 不允许以删除功能、隐藏入口或写死假数据的方式换取更好看的界面。
- 复用已有组件优先；只有当共享组件确实阻碍一致性时才重构。
- 完成后运行项目现有构建和测试，修复本次修改引入的编译错误、资源错误和明显运行时问题。

## 11. UI 验收清单

提交前逐项检查：

- [ ] 所有主要页面使用同一套颜色、字号、圆角和间距 Token。
- [ ] 首屏视觉重点清晰，用户能迅速识别页面主题和主要操作。
- [ ] 没有无意义的渐变、过量卡片、重阴影、多色按钮或风格不统一的图标。
- [ ] 主要按钮、输入框、列表行和导航具备清楚的交互反馈。
- [ ] Loading、Empty、Error、Success、Disabled 等状态均有设计与实现。
- [ ] 浅色和深色模式都可读，状态色的含义一致。
- [ ] 字体放大后没有明显裁切、重叠或操作按钮溢出。
- [ ] 点击目标尺寸、语义描述和 TalkBack 焦点顺序合理。
- [ ] 小屏、横屏、窗口缩放和大屏下无明显布局崩坏。
- [ ] 原有业务流程仍然完整，未使用假数据或空点击占位。
- [ ] 项目构建与相关测试通过；未引入无关依赖或大规模架构变更。
